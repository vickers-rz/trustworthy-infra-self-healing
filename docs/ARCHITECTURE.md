# Architecture

## Control loop

```text
OBSERVE → BUILD EVIDENCE → DIAGNOSE → PROPOSE → CLASSIFY RISK → AUTHORIZE → SIMULATE → CANARY → EXECUTE → VERIFY → LEARN
                                                          │                                  │
                                                          └──── deny / escalate               └── watchdog → abort/rollback
```

The architecture intentionally separates components that **form beliefs** from components that **hold authority**, and now also separates **evidence authority** from proposal generation.

## Three-input authorization model

Authorization consumes three independently sourced objects.

### 1. Remediation Proposal — probabilistic/untrusted

May be generated by rules, ML, RAG, an LLM, or a planner. It contains:

- stable hypothesis ID, type and confidence;
- `evidence_bundle_id` plus selected `evidence_ids`;
- advisory `estimated_risk`;
- typed semantic action;
- preconditions;
- verification criteria;
- typed rollback/compensation action.

It does **not** contain authoritative execution permission or provenance-bearing evidence objects.

### 2. Execution Context — trusted runtime state

Supplied by control-plane identity, policy, operator, and approval systems. It contains:

- authenticated actor identity;
- granted authority class;
- human approval provenance;
- operator override state;
- policy version;
- environment;
- explicit decision time.

Decision time is trusted input so evidence freshness decisions are deterministic and replayable.

### 3. Evidence Bundle — trusted evidence-plane state

Supplied independently of the proposal. It contains:

- source/collector provenance;
- observation and collection timestamps;
- freshness metadata;
- source trust metadata;
- optional integrity digests;
- supporting/contradicting/context relations;
- explicit missing-evidence declarations.

The proposal may reference items inside this bundle but cannot rewrite them.

```text
Proposal ────────────────┐
                         │
ExecutionContext ────────┼─> bind/resolve evidence
                         │          │
EvidenceBundle ──────────┘          ▼
                           Risk + Freshness Policy
                                    │
                                    ▼
                           Remediation Guard
                                    │
                                    ▼
                                 Executor
```

## Evidence layer

Inputs may include metrics, logs, traces, Kubernetes events, cloud control-plane events, Git history, deployment revisions, runbooks, postmortems, dependency topology, and operator annotations.

The Evidence Plane normalizes these sources into `EvidenceBundle` objects before diagnosis/authorization. RAG may retrieve from evidence/knowledge sources, but retrieval does not make retrieved text authoritative.

### Freshness policy

The first deterministic freshness policy distinguishes operational evidence from reference evidence.

Operational evidence includes metrics, logs, traces, Kubernetes state/events, changes, topology, and operator annotations. If selected for mutable remediation, operational evidence must have known freshness and still be fresh at trusted decision time.

Runbooks and historical incidents may provide context with unknown freshness, but cannot alone establish current operational state. Mutable remediation requires at least one selected fresh operational evidence item.

## Diagnosis layer

Rules, statistical detectors, classical ML, and LLMs may jointly produce hypotheses and rank likely root causes. Outputs are uncertain by design and must preserve confidence plus supporting and contradicting evidence references.

A diagnosis can reference trusted evidence IDs; it cannot rewrite the evidence object's provenance.

## Proposal layer

A planner converts a hypothesis into a typed `Proposal`. The proposal describes semantic action, advisory estimated risk, preconditions, rollback, verification criteria, and evidence IDs.

Arbitrary shell and inline trusted-evidence metadata are not part of the proposal schema.

## Deterministic risk classifier

The risk classifier derives **effective operational risk** from trusted semantic action rules and, in future phases, blast radius, environment, service criticality, statefulness, dependency topology, and other control-plane facts.

A proposal may estimate its own risk, but that value is advisory only.

If a proposal reports a lower risk than the deterministic classifier derives, the MVP fails closed. This turns risk disagreement into an auditable safety signal rather than a privilege-escalation path.

## Remediation Guard

The guard is deterministic and fail-closed. It evaluates:

- proposal/hypothesis identity;
- trusted EvidenceBundle validity;
- proposal bundle/item reference binding;
- incident identity consistency;
- trusted decision time;
- evidence freshness policy;
- typed action schema validity;
- trusted execution authority;
- deterministic effective risk;
- proposal/effective-risk disagreement;
- blast radius (future implementation);
- human/operator override;
- preconditions;
- rollback requirement;
- verification requirement;
- explicit approval provenance where required;
- policy version and provenance.

Model confidence cannot override a denied policy decision.

## Typed semantic actions

The action boundary is a closed union rather than free-form `map[string]string` command parameters.

Initial types include:

- `restart_workload`;
- `rollback_deployment`;
- `scale_workload`;
- `drain_node`;
- `uncordon_node`;
- `failover_database`.

Each action owns a typed payload and validation rules. Rollback/compensation is itself represented as a typed action.

## Kubernetes observation substrate

`HealingPolicy` is currently observe-only. The controller reads Deployments, records status, uses a cache field index for event routing, and has target-side `get/list/watch` RBAC only.

A Kind e2e test runs the real controller under its restricted ServiceAccount and verifies that Deployment patch is denied by the Kubernetes API server.

This observation substrate will become an Evidence Plane adapter in the next phase; it does not currently perform remediation.

## Semantic executor

Approved actions map to trusted implementations. Parameters are validated before execution; the executor never accepts generated command text as an execution primitive.

A future mutation-capable executor should additionally require a cryptographically/auditably bound authorization artifact so direct executor calls cannot bypass the guard.

## Independent watchdog

The watchdog owns deadlines, abort signals, and safety invariants. A future production design should deploy it in a distinct failure domain from the planner/controller so LLM outage, RAG failure, controller crash, or network partition cannot remove the escape path.

## Verification

Verification uses externally observable postconditions: SLOs, readiness, error rate, latency, saturation, dependency health, and application-specific invariants. The proposing model does not self-certify success.

## Learning

Outcomes may update incident similarity, remediation ranking, confidence calibration, and hypothesis priors. They may not directly rewrite hard policy, evidence provenance, source trust, or execution authority. Policy evolution is an explicit reviewed artifact, ideally GitOps-managed.

## Package boundaries

```text
internal/domain      typed proposal/action/context/evidence contracts
internal/evidence    deterministic evidence/freshness policy
internal/risk        deterministic effective-risk classification
internal/policy      deterministic authorization
internal/executor    semantic action boundary
internal/controller  observe-only Kubernetes reconciliation
```

Future packages will add trusted evidence adapters, source registry, diagnosis, audit, watchdog, simulation, verification, and provider integrations.
